# SDD 产物约定

以下结构是实现建议，不是固定表单。优先沿用项目已有术语和格式，但必须保留这里定义的判断信息。

## 项目级规格

### `specs/mission.md`

写项目为什么存在，而不是技术方案。推荐覆盖：

```text
# Mission
## 问题、价值与目标用户
## 关键利益相关方及其诉求
## 约束、边界与明确不做什么
## 可判断真假的成功状态
```

不要写“体验良好”“性能优秀”这类无法验收的完成标准，改成可观察的状态或阈值。

### `specs/tech-stack.md`

写项目的技术边界。推荐覆盖：

```text
# Tech Stack
## 项目类型、入口与交付方式
## 语言与运行时
## 核心框架、库、存储及其选择原因
## 构建、测试与验证命令
## 开发/生产依赖和版本策略
## 安全、兼容、部署等约束
## 已知空白或待清理项
```

测试命令必须来自仓库、CI 配置或实际验证；不确定的命令写为待确认，不能伪装成可执行事实。

### `specs/roadmap.md`

写高层次交付顺序，每个 phase 用一句话说清完成后项目能做什么：

```text
# Roadmap

## Phase 1: <名称> ✅
**目标：** <已完成能力>

---

## Phase 2: <名称>
**目标：** <完成后可独立交付的能力>

---

## Later / Backlog
- <只列方向，不展开任务>
```

phase 超过三四行仍说不清时，通常应拆分。phase 之间按交付顺序排列，而不是按代码层或团队分工排列。

## Feature 规格

### `requirements.md`

定义 feature 的边界和关键选择，推荐覆盖：

```text
# Requirements: <功能名>
## 范围
## 范围外（必要时注明后续 phase）
## 使用者可见行为
## 关键决策及原因
## 背景与约束
## 未决问题及暂定处理
## 兼容性约束（仅存量项目适用）
```

“行为”覆盖正常流程、空状态和失败路径，写用户看到什么、系统发生什么。数据结构、文件位置或接口选择属于“决策”，必须说明原因。

### `plan.md`

从 requirements 自然拆出按实现顺序排列的 task group。每个 group 应可独立 review：

```text
# Plan: <功能名>
## Group 1 — <描述性名称>
1.1 <可执行动作>
1.2 <可执行动作>

## Group 2 — <描述性名称>
...

## Group N — 测试
...

## 备注
- 从 requirements.md 出发。
- 遵守 specs/tech-stack.md。
- 未经批准不新增依赖。
```

group 名称跟随真实工作内容，不要套用空洞分类。至少包含测试；如有轻量自检，可另列“验证”group，但它不能替代 `validation.md`。存量项目可把“适配任务”与“新增任务”分开。

### `validation.md`

写成另一人照着就能执行并判断通过/失败的验收清单：

```text
# Validation: <功能名>
## 自动化检查
- 命令：...
- 期望：...

## 场景验证
- 场景：...
- 输入/步骤：...
- 期望结果：...

## 输出文本检查
- 检查位置：...
- 期望语气与措辞：...

## 完成条件
- 所有自动化检查通过
- 场景验证无阻塞失败
- 规格与实现一致
- roadmap 可标记完成
- changelog 已更新（如项目启用）
```

场景至少考虑主流程、空状态/首次使用、错误输入、异常数据和必要时的干净环境。存量项目追加原有测试或核心人工回归。删除不适用项，并增加项目特有检查。

## 一致性检查

写完后把三份 feature 规格交叉检查一次：

- `requirements.md` 的每个范围项都有 plan task 和 validation 证据。
- `plan.md` 没有实现 requirements 之外的功能。
- `validation.md` 能证明每个使用者可见行为，而不只是证明代码能编译。
- 未决问题如果会影响实现或验收，不能留到编码后再猜。
