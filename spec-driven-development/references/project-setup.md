# 项目规格初始化

本文件只在建立或重建项目级规格时读取。先判断项目是新项目还是存量项目；两者最终都产出同一组顶层规格。

## 新项目

1. 读取项目输入，例如 `prd.md`、用户描述、已有文档和当前目录。区分明确要求、合理推断和未决问题。
2. 在写文件前，与用户确认真实会影响规格的三类信息：
   - 范围：当前项目或阶段做什么、明确不做什么。
   - 决策：技术、产品、交付方式或优先级上必须由用户拍板的选择。
   - 背景：目标用户、使用场景、兼容要求、合规约束、品牌或语气等上下文。
3. 创建 `specs/`，完成 `mission.md`、`tech-stack.md`、`roadmap.md`。内容参考 [artifacts.md](artifacts.md)，格式可随项目自然生长。
4. roadmap 是高层次交付顺序，每个 phase 必须能独立 review 和交付；不要把它写成细碎任务清单。
5. 写完停在这一步，交给用户复查，不自动开始 feature 实现。

## 存量项目

存量项目采用渐进式引入。不要为了补规格而先大规模重构旧代码，也不要把全部历史代码一次性反向文档化。

### 1. 建立全局认知

只读探索仓库，不写规格：

- README、产品文档、依赖文件、配置、入口和部署说明。
- 目录组织、核心业务逻辑位置、测试入口和运行命令。
- Git 历史、现有 issue、TODO/FIXME、CHANGELOG 中可确认的功能与决策。

先向用户给出简短发现摘要，包含项目类型、已确认的技术栈、核心模块、不清楚或互相矛盾的地方。对用户理解错误的地方先纠正，再进入下一轮。

### 2. 反向建立 `mission.md`

根据代码和文档起草项目为什么存在、服务谁、核心价值、边界和不做什么。每条重要信息标记为：

- `[事实]`：代码、配置或文档能明确证明。
- `[推断]`：理解合理但仍需用户确认。

商业目标、目标用户、优先级和“不做什么”通常无法从代码证明，必须由用户确认。不要让 `[推断]` 以事实口吻留在最终规格里。

### 3. 反向建立 `tech-stack.md`

以依赖文件和实际代码为准，记录语言、运行时、框架、存储、测试、构建与部署。每个核心选择尽量写“用了什么、为什么、在哪里使用”。区分开发依赖和生产依赖，并标记：

- 与代码不符或未在依赖中声明的技术。
- 已停止维护、仅孤立使用或与项目约束冲突的依赖。
- 当前没有但可能会影响后续工作的已知空白。

“应当清理”属于推测或建议，除非用户确认，否则不要直接改实现。

### 4. 反向建立 `roadmap.md`

根据 Git 历史、issue、CHANGELOG 和 TODO/FIXME 还原高层 phase：

- 已交付能力标 `✅`，必要时用一句话记录能从证据确认的关键决策。
- 未完成事项按交付能力重组为后续 phase，不照搬零散 TODO。
- 范围模糊、优先级或顺序由用户补充确认。

### 5. 选择第一个 feature

第一个 feature 的目标是验证 SDD 能在这个项目中跑通，而不是一次证明旧代码可以被全面改造。优先选择影响面小、依赖少、容易回滚的工作，例如：

- 新页面、新视图、新 CLI 命令或新 API 接口。
- 范围清楚且独立的小 bug 或 TODO。

避开核心业务重构、数据库结构迁移、认证/权限替换和多模块依赖升级。如果 roadmap 的下一个 phase 是这类高风险工作，先把其中独立性强的子任务拆出来。

完成第一个 feature 后必须 replanning：把这次运行暴露出的项目事实、约束和 roadmap 偏差同步回顶层规格，再继续常规 phase loop。

## 顶层规格复查点

写完后逐项检查：

- `mission.md` 是否能判断项目成功与否，并明确边界。
- `tech-stack.md` 是否与技术证据一致，测试命令是否真实可运行。
- `roadmap.md` 是否是高层交付顺序，而不是实现任务列表。
- 事实、推断、未决问题是否有清晰区分。
- 是否已经停下来等待用户确认，而没有擅自开始代码修改。
