# Feature 交付闭环

本文件只用于 roadmap 中的一个 phase。先读取最新顶层规格和 roadmap，确认目标 phase，再开始写 feature 规格。

## 1. 选择与确认 phase

1. 找到 roadmap 中第一个未完成且满足前置条件的 phase。
2. 读相关代码、文档和测试。存量项目尤其要先确认现有契约，不能凭目录名或历史印象写约束。
3. 在写规格前，与用户确认本次 feature 的范围、决策和背景；把未决问题连同暂定处理方式写清楚。
4. phase 如果过大，按可独立交付的边界拆分；不要用一个巨型 feature 吞掉多个 roadmap phase。

## 2. 创建 feature 规格

项目位于 Git 仓库时，按用户或仓库约定创建 `phase-N-<kebab-name>` 分支。随后创建目录：

```text
specs/YYYY-MM-DD-feature-name/
├── requirements.md
├── plan.md
└── validation.md
```

三份文件必须互相一致，具体内容参考 [artifacts.md](artifacts.md)。

存量项目还要：

- 在 `requirements.md` 中加入“兼容性约束”：涉及的现有模块、必须保持的行为、接口或数据契约。
- 在 `plan.md` 中单列“适配任务”，把为了接入新功能而改动的旧接口、配置或数据结构与“新增任务”分开。
- 在 `validation.md` 中加入原有测试/启动流程，以及项目没有自动测试时必须人工回归的核心路径。

写完规格后先停，等待用户 review。规格未确认时不要进入实现。

## 3. 实现

1. 严格从 `plan.md` 的任务组出发，并以 `requirements.md` 和项目技术约束为准。
2. 按实现顺序推进，每个任务组保持可 review；主动把无关改动推到后续 phase。
3. 未确认前不新增依赖、不改变公共契约、不扩张到未写明的范围。
4. 发现规格缺失、冲突或错误时，同步更新当前 feature 的三份规格，并让实现与更新后的规格一致。
5. 只修改 `specs/roadmap.md`、`CHANGELOG.md` 等项目关闭步骤负责的文件时，应在规格阶段处理，不以实现顺手改为由覆盖。
6. 完成实现者自检，例如编译、服务启动、关键命令和最小 smoke test。实现者自检不能替代正式验证。

## 4. 独立验证

正式验证使用干净上下文，不让实现者自验。若环境支持独立 agent 或会话，把 `validation.md` 和运行所需材料交给它；否则向用户提供一段可直接用于新会话的验证提示。

验证者必须：

- 只读规格、执行检查、记录真实结果，不修代码。
- 逐条标记“通过 / 失败 / 跳过”，跳过项说明原因。
- 对失败项写明期望、实际结果、复现步骤和相关证据。
- 检查自动化命令、场景行为、边界与失败路径、可见文本以及存量功能回归。

验证报告由用户复查并逐条决定：

- 实现偏离规格：回到实现修复。
- 规格本身不合理：先改正规格，再决定实现。
- 无法判断：把具体失败项交回实现者确认根因和真伪，不要直接接受含糊结论。

修复后重新验证受影响项，直到完成条件满足或用户明确接受残余风险。

## 5. 收尾

1. 根据当前 feature 分支的 Git 提交记录创建或更新 `CHANGELOG.md`。最新日期在前；每个提交一条简短 bullet；遵循项目已有格式。
2. 在 `specs/roadmap.md` 中把已交付 phase 标为 `✅`。
3. 检查规格、实现、验证报告和 changelog 是否一致。
4. 提交、切回主分支、合并和删除 feature 分支仅在用户任务授权交付且仓库惯例允许时执行；否则报告待执行的收尾操作。不要自行改写或丢弃用户已有改动。

## 6. Replanning

完成一到两个 phase、出现新的全局要求，或发现剩余 roadmap 拆分不合理时，先 replanning。

1. 读取顶层规格、已交付成果和用户的新决策。
2. 说明准备修改哪些顶层文件、为什么以及会影响哪些 phase，取得用户确认。
3. 只更新 `mission.md`、`tech-stack.md`、`roadmap.md` 中真正受影响的内容，不顺手改实现。
4. 顶层规格写完后停止。代码改动作为新的 feature 或 phase，重新经历“规格 → 实现 → 验证 → 收尾”。

仅当改动极小、用户同意且所有 diff 能在一次 review 中看清时，才考虑在同一轮同时修改规格与实现。

## 完成当前轮

在进入下一轮前，清楚报告：

- 本次 phase 的交付结果和当前状态。
- 实际执行的验证及报告位置；没有执行的验证不得标成通过。
- 仍未决的规格偏差、风险或用户决策。
- roadmap 下一个可用 phase，但不自动进入下一轮，除非用户明确要求连续完成。
